# Every npm script, what runs it, and what breaks without it

**Status:** recorded 2026-09-15 · [869f17h73](https://app.clickup.com/t/90121749478/869f17h73)

There are 138 scripts in `package.json` and, until this existed, no way to tell
what any given one was for, who called it, or whether it still mattered.

## What is generated, and what is not

The subtask asks for four things per row — name, purpose, caller, and what breaks.
Three are derivable and one is not, and that difference decides this file's shape.

| Column | Generated? | From |
| --- | :--: | --- |
| Name | yes | `package.json` |
| Reached by | yes | lanes, workflows, other scripts, docs |
| What breaks | yes | follows from the caller |
| Purpose | **no** | see below |

**Purpose is deliberately absent.** 138 hand-written purpose lines would mostly
restate the command — `test:ci-routing` *"runs the CI routing tests"* tells a
reader nothing they could not see — and would rot the moment a command changed.
Authored prose appears only where it already earns its place: the entries in
[`scripts/npm-script-registry.mjs`](../scripts/npm-script-registry.mjs), which
exist to explain the scripts that **look** orphaned and are not.

## How "what breaks" is derived

A script that **is** a lane's command breaks that lane and nothing else. That is
the strongest answer available, so lanes are checked first, then workflows, then
other scripts, then documentation — a runbook naming a script is a real
reference, and it is the one kind where what breaks is *a human following a doc*.

`unclassified` is the only failing state. It means a script resolves to no caller
and has no registry entry, and it is what makes the subtask's done-condition real:
**a new script without a row fails the lane.**

## The registry is the source for the CI matrix, in both directions

`SCRIPT_SUITES` in [`scripts/ci-check-routing.mjs`](../scripts/ci-check-routing.mjs)
is the single definition of every lane and its command.
`.github/workflows/test.yml` carries the same list twice, as shell fallbacks, and
`ci-check-routing.spec.ts` asserts the workflow matrix is **identical** to
`SCRIPT_SUITES` — so that duplication cannot drift.

**869f135tn corrected what this section used to claim.** It said both halves of
the done-condition held. Only one did.

- **Registry → package.json (check C).** A lane naming a script `package.json`
  does not have fails. This is what the section claimed, and until 869f135tn it
  could not happen: the check asked whether the lane command *contained* any of
  the script names as a substring, and two of them are `ng` and `test`. Every
  lane command is `npm run <something>`, so every one of them contains `test`.
  Deleting a lane's real script left the check green. It now extracts the
  `npm run <name>` tokens and matches them exactly.
- **package.json → registry (check D).** Every `test:<id>` script must be the
  `<id>` lane. This direction did not exist. Without it, adding
  `test:my-new-guard` and forgetting the `SCRIPT_SUITES` entry produced a guard
  nobody ever ran, while every check stayed green — the script *was* classified,
  because something referenced it. Eight `test:` scripts are deliberately not
  lanes and are allowlisted with a reason in `NON_LANE_TEST_SCRIPTS`.

The same substring bug sat in the caller column, where it did not fail the lane —
it just published wrong answers. `ng` was listed as reached by eleven workflows,
because "ng" occurs inside the word *running*; `dataset:measure` was attributed to
`test:dataset-measurements`, which invokes `dataset:measurements`; and `watch` was
attributed to two scripts that only pass `--watch=false`. The caller match is now
bounded by `[\w:@./-]` rather than being a raw substring.
